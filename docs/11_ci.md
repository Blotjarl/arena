# Step 11 — CI Pipeline (R-D5)

R-D5 requires the automated test suite (Jest unit tests, Playwright end-to-end tests) to run in a
continuous integration pipeline on every change proposed to the shared repository. Before this, every
merge to `main` was gated only by whoever reviewed the PR running tests locally — `.github/workflows/ci.yml`
is what makes that automated and enforced.

## Trigger

`on: push` and `on: pull_request`, both with no `branches:` filter — this covers every branch the project
uses (`main`, `shared`, `server`, `client`, `api`), not just `main`.

## Jobs

| Job | What it runs | Layout |
|---|---|---|
| `test` | `npm run typecheck -w @arena/<workspace>` then `npm run test -w @arena/<workspace>` | Matrix over `[shared, server, client, api]`, `fail-fast: false` |
| `e2e` | `npm run test:e2e` (the Playwright suite) | Single job |

**Why a matrix for `test` instead of one job:** this project's four packages have four different owners
working on independent branches in parallel (`packages/00_master_context.md` §2.1). A matrix gives each
workspace its own pass/fail check in the PR UI, and `fail-fast: false` means a client-only failure never
hides whether server/api/shared are green. The tradeoff is a bit more workflow setup (threading a
workspace name through a few steps) — worth it here since the whole point of this prompt is per-track
visibility, not just an aggregate green/red.

Every step calls the same npm scripts already established for local/reviewer use
(`npm run typecheck`, `npm run test`, `npm run test:e2e`) — nothing about how these packages get tested was
reinvented for CI.

## Postgres for `packages/api`

`packages/api`'s Jest suite (e.g. `PgPool.test.ts`, `PlayerRepository.test.ts`, `ApiMain.test.ts`) talks to
a real Postgres, hardcoded to `postgresql://arena:arena@localhost:55432/arena_test`. The `test` job's `api`
leg reuses `docker-compose.test.yml` verbatim via the npm scripts that already wrap it
(`npm run test:db:up` / `npm run test:db:down`), then polls `docker compose exec postgres-test pg_isready`
until it accepts connections before running tests.

This deliberately does **not** use a GitHub Actions `services:` Postgres container. A `services:` container
starts before the checkout step, so it can't apply `packages/api/schema.sql` via
`docker-entrypoint-initdb.d` the way `docker-compose.test.yml` does — using one would mean inventing a
second, CI-only schema-application mechanism. Running `docker compose up` as a normal step, after checkout,
doesn't have that problem, and `ubuntu-latest` runners already have Docker installed.

## The `e2e` job

`npm run test:e2e` turned out to already be fully self-contained (verified by running it locally end to
end, not assumed from reading the config): root `package.json`'s `pretest:e2e` hook builds
`packages/shared`, and `e2e/global-setup.ts` brings up `docker-compose.test.yml`'s Postgres itself
(it calls `npm run test:db:up` and polls for readiness), then starts real `ApiMain`/`ServerMain` in-process,
before `playwright.config.ts`'s `webServer` starts the client's Vite dev server. So the `e2e` job is just:
checkout, install Node deps, `npx playwright install --with-deps chromium` (the config defines no
`projects:`, so the default project is chromium-only), then `npm run test:e2e`. On failure, the job uploads
`playwright-report/` and `test-results/` as build artifacts for debugging.

## Verified

**Locally**, for every job/step exactly as scripted in `ci.yml` (same commands, same working directory,
Docker available locally): all four workspaces' `typecheck` + `test` pass (`shared` 18 tests, `server` 155,
`client` 132, `api` 84, including the Postgres-backed suite against a `docker-compose.test.yml` instance
started and torn down the same way the workflow does it); `npm run test:e2e` passes standalone with no
manual setup beyond that one command.

**On GitHub Actions itself**: see the note in the commit that introduces this file / the PR history around
it for whether a real run was pushed and observed to go green, and whether a disposable test PR was opened
to confirm PR-level check visibility — don't assume from this file alone, since it doesn't self-update.
